# TikHub 数据采集替代评估

评估日期：2026-09-14。范围：当前工作区源码、账号配置、已有快照、平台公开文档与少量只读验证。

用户已确认：全部账号都可以由运营人员配合授权登录。该确认支持后台采集方案，但不代表已经完成登录，也不等于各平台开放 API 权限已经获批。

## 1. 结论与选型

可以将“移除 TikHub 运行依赖”设为改造目标。推荐 **授权运营后台采集为主，平台官方 API 按权限接入，公开页面与直接 HTTP 请求补充**。保留现有 Python 调度、大屏 JSON 和评论提醒链路，按平台替换采集适配器。

不能在未登录验证前承诺全部平台、全部历史、全部字段与全部二级回复都能等价获取。后台可登录仍可能受到角色权限、历史时间窗口、统计延迟及页面可见范围限制。真正需要验收的是数据覆盖和持续运行能力，而不仅是脚本能否打开网页。

三种方式的定位：

| 方式 | 适用场景 | 主要代价 | 本项目建议 |
| --- | --- | --- | --- |
| 官方 API，由代码直接调用 | 已授权账号的数据和评论，且应用具备对应能力 | 应用接入、权限申请、令牌续期；不一定覆盖历史全量 | 对具备权限的账号优先使用 |
| 浏览器访问后台，读取正常加载的响应或自动下载报表 | 自有账号的作品、数据分析、评论管理 | 登录会话维护、页面变化、时间窗口、需要扫码恢复 | 本次改造的主要路线 |
| 直接 HTTP 请求或公开页提取 | 无需额外权限的公开详情与统计 | 可能缺少字段、需要浏览器上下文、访问限制 | 作为补充，逐接口验证 |

页面截图识别只适合最后的少量补充；数值、ID、分页与评论关系优先取结构化响应，其次取官方导出，最后才读取 DOM。浏览器发起的正常请求仍是平台接口，区别在于不再经过 TikHub；不能只替换 base URL。

## 2. 当前依赖的完整范围

静态 AST 扫描发现 **27 个不同的 TikHub API 路径**。这里统计包含搜索、失败回退、可选补全和评论发现路径，不表示每次运行会全部调用。

| 入口 | 文件内不同路径数 | 用途 |
| --- | ---: | --- |
| `pipeline/fetch_data.py` | 13 | 抖音、B站、视频号账号解析、作品列表、详情补全 |
| `pipeline/fetch_article_data.py` | 7 | 知乎、小红书、公众号资料与文章、公众号可选互动补全 |
| `pipeline/comment_monitor.py` | 11 | 四平台评论、二级回复、小时级新作品发现；与主采集器有重复路径 |

配置共 24 个账号，其中 14 个受此次替代影响，覆盖 6 个平台体系；公众号在配置中拆成服务号、订阅号两个标识。

| 平台 | 账号数 | 本地历史快照中的内容记录数 | TikHub 当前职责 |
| --- | ---: | ---: | --- |
| B站 | 2 | 130 视频 | 资料、搜索回退、投稿、视频详情、评论及回复、新作品发现 |
| 抖音 | 2 | 119 视频 | 账号解析与搜索、Web/App 投稿回退、评论及回复、新作品发现 |
| 视频号 | 3 | 63 视频 | 短号转换、账号资料、作品、评论及回复、新作品发现 |
| 小红书 | 1 | 45 笔记 | 资料、笔记列表与互动、评论及回复、新笔记发现 |
| 知乎 | 2 | 109 文章 | 资料与专栏文章列表；当前不是回答采集 |
| 公众号 | 4 | 2,705 文章/图片消息 | 可选名称搜索、历史分页、可选逐篇互动补全 |

以上来自 2026-08-27 的本地快照，合计 3,171 条受影响的内容记录，不是本次重新采集结果，也不代表当前线上总量。两个抖音账号在该快照中为 `stale`，两个知乎账号为 `partial`，公众号也有历史分页未覆盖的账号。

不需要替换的现有通道：CSDN 3 个、百家号 3 个、电子发烧友 1 个、搜狐 1 个、今日头条 2 个，共 10 个账号。前四类已使用公开 HTTP/网页采集，今日头条已使用浏览器采集。

当前代码中的评论正文适配仅覆盖 **B站、抖音、小红书、视频号**；其他平台只比较大屏里的评论数。不能把旧方案说明中的更多平台能力算作当前已实现功能。

### 容易漏掉的依赖

- `comment_monitor.py:315` 的 `discover_latest_contents()` 独立调用平台作品接口，每小时发现每日大屏刷新后新增的内容；抖音还直接复用 `DouyinAdapter`。它也必须迁移。
- `fetch_data.py` 主入口要求 TikHub Key，图文入口统一创建 TikHubClient；只修改某个采集类还不足以解除配置依赖。
- B站、抖音都有资料或接口失败回退；公众号名称搜索和互动补全是可选调用，仍属于清理范围。
- `docker-compose.yml` 默认 `--no-enrich-bili`、公众号最多 5 页；评论为 `--limit 10 --max-age-days 90 --max-pages 20 --no-replies`。这是仓库默认配置，未核验生产环境是否覆盖它。评论 `limit` 按账号生效，二级回复当前默认关闭。
- 当前评论状态使用 `data/comment_state.json`，提醒另有持久化文件链路；本次按当前 JSON 实现设计迁移，不假定项目仍使用早期 SQLite 版本。

## 3. 分平台替代路线

### B站：第一批落地，公开详情已验证

主路线：授权后的创作中心获取账号、投稿清单和后台统计；公开详情请求补全可获取的字段；评论管理或作品评论页面获取一级评论和完整回复分页。具备开放平台权限时，将对应后台采集切换为官方 API。

本次对项目已有账号和视频做了 3 次公开只读请求，未使用 TikHub Key、未加载账号 Cookie：

| 请求 | 结果 | 说明 |
| --- | --- | --- |
| `GET api.bilibili.com/x/web-interface/view?bvid=BV19R8i6KEQZ` | HTTP 200，`code=0` | 返回播放、点赞、收藏、投币、分享、弹幕、评论数；该次播放 558、点赞 7 |
| `GET api.bilibili.com/x/relation/stat?vmid=3537118127197066` | HTTP 200，`code=0` | 返回粉丝相关字段 |
| `GET api.bilibili.com/x/space/wbi/arc/search`，附账号与分页参数 | HTTP 412 | 未签名、无登录上下文的列表请求不能直接使用；未进一步尝试规避校验 |

因此，视频详情替换已有实测支撑，账号全量列表和评论分页仍需通过正常登录后台验证。一次成功不代表持续稳定。B站官方开放平台列有授权后的用户和稿件数据能力，但具体权限需查看接入应用。[官方文档](https://open.bilibili.com/doc)

ID 继续保存为字符串，保留 `bvid`、`aid`、`cid`，不能把 AV/BV 或超过 JavaScript 安全整数范围的 ID 转为浮点数。粉丝和详情不要求每次重新搜索作者。

### 抖音：授权后台主采，官方能力按权限替换

主路线：固定账号身份后，从创作者后台作品管理、数据中心、评论管理采集。公开作品列表可做交叉校验。固定保存公开号与内部账号 ID 的映射，取消每轮按昵称付费搜索。

目标保留作品元信息、赞/评/藏/分享、一级评论和二级回复。后台能够返回的播放量单独补齐；下载次数等字段仍按实际可见能力记录，不预设一定存在。

抖音官方文档列出 `video.comment` 互动管理权限及 `/video/comment/list/`、`/video/comment/reply/list/`；需应用权限和账号授权。官方授权说明也提示数据经营能力需要 PC 授权，因此不能把“扫码登录创作者后台”直接视为已拿到可调用 API 的令牌。[评论接入方案](https://open.douyin.com/platform/resource/docs/ability/interaction-management/video-comment-management-solution) · [授权说明](https://partner.open-douyin.com/docs/resource/zh-CN/dop/develop/sdk/mobile-app/permission/overall-permission)

验收重点：两个现存 `stale` 账号的真实作品范围；置顶作品与翻页；评论顺序；旧评论上的新回复；后台和公开页数据口径。官方内容标识若与现有 `aweme_id` 不同，先建映射，不直接替换主键。

### 小红书：数据后台与评论页面分别验证

主路线：创作服务平台采集笔记列表、账号数据和笔记分析；评论从后台可用管理入口或正常登录后的笔记页提取，二级回复必须展开/分页读取。

后台预计可补充目前为 `null` 的阅读类指标，但具体是阅读次数、观看次数还是曝光量，需要实测后定义映射。不能把曝光直接写入 `read`，也不能承诺网页版一定返回分享次数。

本次访问官方入口已跳转到登录页，页面显示创作发布和数据分析功能；未登录采集业务数据。[创作服务平台](https://creator.xiaohongshu.com/)

保留 `note_id` 与用户 ID；评论定位所需的临时参数在每次正常页面加载后取得，不当作永久内容 ID。主风险是登录有效性、列表分页、字段可见范围及二级回复覆盖。

### 知乎：替换文章链路，不把回答混入旧统计

主路线：登录后的用户文章页或创作中心，读取文章列表与作者资料；若有文章分析数据，再补阅读量。公开页面响应、结构化页面数据可用于已有公开字段。

当前 `ZhihuCollector` 获取的是专栏文章，不包含回答。改造保持该统计范围，新增回答须另设内容类型与主键，不能直接混入现有文章总量。

账号 `url_token`、文章 ID、作者校验应保留。赞同、点赞、收藏、评论等字段逐项比对；创作后台没有给出的字段保持未知。本次未登录验证知乎后台，路线为待验证设计。

知乎评论正文属于可选功能扩展，不计入本轮 27 个 TikHub 路径的等价替代。

### 公众号：后台覆盖历史，官方 API 按资格分流

4 个账号分别核查主体、认证、开发接口权限和运营角色。推荐官方 API 能覆盖的部分直接取数，后台“已发表内容/数据分析”与自动导出补足历史。

本次已通过浏览器读到微信现行官方文档：`freepublish/batchget` 支持成功发布列表，`count` 为 1–20；适用范围表显示公众号“仅认证”、服务号可调用，并解释“仅认证”为企业主体已认证账号。文档列有 `48001 api unauthorized`。因此不能假定 4 个账号都能直接调用。[获取已发布的消息列表](https://developers.weixin.qq.com/doc/subscription/api/public/api_freepublish_batchget.html)

统计接口也有版本和历史边界：微信已将旧 `getarticletotal` 标为停止维护，并指向新的发表内容统计接口。本次核验的新 `getarticleread` 仅支持逐日查询，结束日最大为昨日，数据存储从 **2025-11-01** 开始，建议次日 8 点后请求；明确返回的是 `read_user` 阅读人数，还包含延迟标记 `is_delay`，公众号和服务号均要求企业主体已认证。它不能直接当作历史累计阅读次数写入现有 `read`，也不能通过每日人数相加得到去重累计人数。旧年份的清单与累计指标须另由后台验证，无法恢复的历史指标保留缺失说明。[旧接口维护提示](https://developers.weixin.qq.com/doc/subscription/api/wedata/news/api_getarticletotal.html) · [新阅读统计接口](https://developers.weixin.qq.com/doc/subscription/api/wedata/news/api_getarticleread.html)

重点处理：

- 当前同时采集普通文章与图片消息，替代采集也要逐类核对，不能只抓普通图文。
- 官方发布记录的 `article_id`、现有 `app_msg_id-idx`、网页 URL 标识可能不同。以账号身份、规范化文章链接和文章序号建立映射，保存原 ID，避免 2,705 条历史内容被重新计为新增。
- 发布列表存在不等于全部历史、各发布方式及图片消息均已覆盖，必须与运营后台清单核对。
- 官方图文数据接口有各自日期参数与查询口径；当期数据、累计值、阅读人数和次数分别保存。不能按“每天增长”累加已经累计的值。
- 不能用素材更新时间代替首次发布时间，也不能把草稿链接或临时链接视为永久发布链接。
- 公众号全量留言与精选留言范围不同。当前项目没有公众号正文评论采集，本轮默认保留计数能力；若扩展全文留言，单独验证后台权限、回复范围及字段。

仅能人工下载报表时可以作为临时兜底，但不能据此宣布已实现全自动替代。自动触发导出、下载、解析并验证成功，才计入自动采集覆盖。

### 视频号：优先做技术验证，是整体项目关键路径

3 个账号全部从官方视频号助手接入：核验登录账号 → 内容管理清单 → 数据中心 → 评论/互动管理。由于没有核实到本项目可直接使用的通用公开视频数据官方 API，计划不依赖该假设。

本次打开 `channels.weixin.qq.com` 跳转到了登录页，只确认入口可达。腾讯官方培训材料曾介绍作品数据分析与表格下载，但材料较早，当前字段、导出范围和评论功能必须登录复核，不能据此承诺全量覆盖。[视频号助手](https://channels.weixin.qq.com/) · [腾讯官方培训材料（2021）](https://training.tencentads.com/uploads/202108/0rhYyjKh_vk9HWG.pdf)

计划以后台作品 ID 建立映射，不再依赖 TikHub 的 `sph → username` 转换。保留旧 `object_id`，验证它与后台 ID 的对应关系；短期媒体下载 URL 不能作为持久主键或长期作品链接。

目标字段为作品、发布时间、播放、赞/评/分享/收藏和粉丝，以及现有评论及回复能力。任何后台不可见字段明确标为不支持或部分覆盖。

关键验收：3 个账号切换是否相互挤掉登录态、是否有独立运营者角色、历史分页能否到达尾页、评论和回复是否有稳定 ID 与时间戳、Linux 容器与登录工作机环境是否可持续运行。

## 4. 可复用部分与必要改造

现有 `ToutiaoCollector` 已实现浏览器加载、监听 feed 响应、滚动分页、结构化解析；`requirements.txt` 已包含 Playwright，采集镜像已安装 Chromium。因此不需要从零建立浏览器运行基础，但各平台业务适配仍须独立完成。

建议新增的组织形式，以下均为设计，尚未实现：

```text
pipeline/providers/
  base.py                  统一结果和能力声明
  sessions.py              账号隔离、登录健康、会话续用
  bilibili.py
  douyin.py
  xiaohongshu.py
  zhihu.py
  wechat_mp.py
  wechat_channels.py

现有 scheduler
  → provider（官方 API / 后台响应 / 导出 / 公开详情）
  → 统一字段、ID 映射、数据完整性校验
  → 现有大屏快照、评论状态、提醒队列
```

统一能力包含账号资料、作品分页、作品指标、评论分页、回复分页、新作品发现。每次分页结果返回 `items`、`cursor`、`has_more`、`complete`、`source`、`fetched_at` 和覆盖说明，不向上层泄漏某个 TikHub 包装结构。

| 文件/模块 | 必要修改 |
| --- | --- |
| `fetch_data.py` | 视频适配器按配置选择 provider；解除 API Key 前置要求；替换固定 `source=tikhub` |
| `fetch_article_data.py` | 替换知乎、小红书、公众号 provider；保留其他直采与导入能力 |
| `comment_monitor.py` | 同时替换正文、二级回复、新内容发现及 TikHubClient 创建；从 provider 读取能力，不能缺 Key 就自动降为计数 |
| `snapshot_utils.py` / `validate_snapshots.py` | 保留缺失字段为 null、失败保留历史、原子写入、账号身份和异常数量校验；增加来源/时间口径检查 |
| `scheduler.py` | 增加任务截止时间、平台失败隔离和超时终止；长时间全量采集不能占用所有小时级评论任务 |
| `docker-compose.yml` / `.gitignore` | 增加不入库的会话持久化位置；明确登录工作机与采集环境；重新定义每平台采集频率 |
| 配置、README、DEPLOYMENT | 配置数据来源、账号会话引用、支持字段与刷新范围，取消 TikHub 必填说明 |
| `tests/` | 保留并适配分页、重试、基线、队列测试，新增跨数据源 ID 映射与真实响应夹具验证 |

### 登录与部署

首次由运营人员扫码；应用仅保存权限受限的会话文件，不在配置、日志或大屏里输出 Cookie/Token。平台与账号隔离浏览器上下文，同一会话串行使用，采集前核验账号 ID，避免切换串号。网页登录失效时显示待登录状态并保留旧数据，停止持续重试该账号。

优先让登录和采集使用同一台长期运行的受管工作机/相同运行环境。若部署仍在 Docker，需要可操作的首次登录及续期入口、持久化会话和固定数据出口；不要默认 macOS Chrome 的整份用户目录能直接搬进 Linux Chromium。

仅靠复制 Cookie 的迁移方案不能作为运行保障。会话可能还依赖浏览器本地状态，具体持久化策略按平台测试。前台大屏继续读取现有 JSON，后台采集工作机可通过受控文件同步或上传步骤交付结果。

### 指标与状态

- 主键继续使用 `account_key + 平台内容 ID`；同一作品的跨账号关联、原作者信息保持一致。
- `read/play` 明确区分累计次数、人数、曝光、按日统计；优先使用精确后台值，DOM 的“1.2万”标记为近似值。
- 保留字段级数据源、采集时间、指标所属日期/时间窗、缺失原因。后台通常存在统计延迟，不能用采集时间伪装指标实时性。
- Provider 内部分清 `session_expired`、`permission_denied`、`rate_limited`、`partial` 等原因；对现有前端映射为兼容的 `stale/partial/error` 状态与说明，避免引入前端不认识的枚举。
- 官方统计口径优先；其他来源只能按明确规则补充，不能以“最后写入”覆盖更可信字段。

### 评论迁移与调度

保留 `monitor_started_at`、已见评论集合及当前提醒队列。先核验跨源评论 ID 与父子关系；能映射的继承原状态。无法映射的旧内容进行一次只建立基线的扫描，保留原启动时间，记录迁移截止时间，不将历史评论集中发为新增提醒。

迁移期间的新事件先缓冲，在新旧扫描覆盖区间重叠且去重成功后再恢复提醒；若无法确认时间戳或 ID 映射，应报告覆盖空窗，不能静默声称无遗漏。扫描分页失败不能推进成功游标或清空已见集合。

建议日常作品发现与指标更新分开，小时级新作品发现使用与主采集一致的 provider；全量历史按平台分批断点补齐。账号后台若提供覆盖全部内容的互动列表，可优先扫描增量，但须验证是否包含旧作品的新回复。

若没有全账号增量评论入口，则新作品评论频繁扫描，旧作品轮转扫描，并明确各自最大检测延迟。只翻“最新一级评论”会漏掉旧一级评论下面的新回复。要求全历史作品评论均在一小时内提醒时，必须测量全量扫描耗时后再承诺，不能默认移除付费接口就能无限扫描。

## 5. 分阶段实施与工作量

工作量是基于现有代码的工程估算，不是报价或承诺；按 1 名熟悉 Python/浏览器自动化的工程师计，账号授权和平台审核等待另计。

| 阶段 | 交付目标 | 估算 |
| --- | --- | ---: |
| 公共层与首轮验证 | provider、账号会话、只读验证；优先确认视频号与公众号的限制 | 3–4 人日 |
| B站 | 2 个账号的作品、指标、一级评论、二级回复及发现链路 | 2–3 人日 |
| 抖音 | 2 个账号、字段映射、后台与官方能力分流 | 3–5 人日 |
| 小红书 | 1 个账号、笔记数据和评论双通道 | 3–5 人日 |
| 知乎 | 2 个账号的资料与文章，不扩充回答/评论业务范围 | 2–3 人日 |
| 公众号 | 4 个账号、权限分流、历史与图片消息、指标映射 | 4–6 人日 |
| 视频号 | 3 个账号、后台采集、ID 映射与评论覆盖 | 5–8 人日 |
| 集成与切换 | 调度、迁移、回归、无 TikHub 运行核验 | 3–5 人日 |

合计 **25–39 人日**，另设至少 7 个自然日的连续运行观察期。若官方 API 权限齐备且后台导出字段完整，取区间下沿；若涉及多个会话恢复、历史补齐或评论结构不完整，接近上沿或需要缩小承诺范围。

实施顺序：先用 B站完成一个纵向闭环，同时在第一阶段就验证视频号/公众号关键限制；之后迁移其余平台。不能等其他平台全部做完才发现视频号后台缺少需要的能力。

首次验证只需要运营人员配合各平台一个代表账号登录，核验作品列表、较旧内容、关键指标和一条多级评论；同平台其余账号仍要逐一核对角色权限，不以一个账号成功代表全部。

成本从 TikHub 请求费用转为浏览器运行资源、运维和适配维护。历史 2026-08-27 快照记录视频 164 次、图文 112 次 TikHub 调用，其中 B站账号累计 142 次；这反映当时配置，当前 Docker 默认已关闭 B站逐条详情补全，不可外推为今天的账单。没有当前计费记录和运行基准，不能准确给出月度节省金额或固定资源规格。

## 6. 切换验收

1. 六个平台体系、14 个账号全部有身份验证结果和明确数据源；账号不可用时能单独报错，不拖垮其他账号。
2. 每个平台完成至少一次多页作品采集；覆盖历史尾页或对历史缺口作逐项说明。原有 3,171 条记录逐项对账，新增内容、下架、权限不可见、ID 映射差异分开统计。
3. 每个平台抽查至少 10 条新旧内容（不足则全查），按相同统计口径和接近时间窗口核对关键字段；舍入或刷新时差单独解释。
4. 四个现有正文评论平台验证一级和二级多页、旧作品新回复、重复分页、评论删除、重启与失败重试。当前关闭二级回复的配置不能视为该项已经验收。
5. 服务启动前/迁移基线中的旧评论不触发新提醒；新事件不因切换重复；迁移观察阶段只生成本地结果，不向收件人试发。
6. 失效会话、403/412/429、超时、页面改版、空列表和数量骤降不会清空历史；来源与更新时间诚实反映缓存。
7. 至少连续观察 7 天，记录每平台计划任务数、成功率、耗时、登录续期次数、字段覆盖和评论延迟。建议目标为有效登录期间按计划完成率 ≥95%，失败均可追踪并补跑；这只是拟定验收门槛，不是已达到的结果。
8. 最终关闭 TikHub provider，并在没有 `TIKHUB_API_KEY`、禁止访问 TikHub 域名的环境中跑通数据采集、评论发现、正文及回复、重启恢复。网络记录验证没有残留付费调用。

过渡期沿用已保存快照作对账基础；如确需新旧来源同时跑，限定代表账号与次数，记录 TikHub 调用量，避免全量双跑额外放大成本。切换失败按平台保留历史快照及显式异常，不隐式重新启用付费 fallback。

## 7. 第三方库选择与证据边界

当前技术栈已经足够支持自建适配器，无需整套搬入爬虫工程。

- MediaCrawler 的仓库列有抖音、小红书、B站、知乎的创作者/评论能力，并采用浏览器登录态，但没有提供本项目的视频号/公众号完整替代保证；仓库声明限制商业用途。因此只把它列为技术路线参考，不默认作为本项目可直接部署的依赖。[项目说明](https://github.com/NanmiCoder/MediaCrawler)
- 常见的 `Nemo2011/bilibili-api` 仓库现已归档，页面声明永久停止维护；本次不将它作为持续维护的选型依据。[仓库当前说明](https://github.com/Nemo2011/bilibili-api)
- “官方文档有能力”“账号已具备权限”“真实登录采集成功”“连续运行稳定”是四个不同证据层级。本轮已完成源码盘点、文档核对、B站 3 个请求和部分入口检查，未完成 14 个账号登录采集，也没有更新大屏快照、修改运行配置或发送提醒。
